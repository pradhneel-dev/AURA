# Security status

The application hashes passwords with scrypt, issues signed bearer tokens, invalidates sessions at logout, and checks active membership and role on protected routes. Customer, dataset, prediction, analysis, recommendation, approval, execution, settings, report, and feedback operations are tenant-scoped. Tenant-specific customer IDs and database unique constraints prevent duplicate collisions. Roles include Owner, Admin, Analyst, and Approver. Tests cover cross-tenant customer access, role denial, PDF auth, invalid WebSocket token rejection, and the approval/execution path. The WebSocket validates the token and membership at connection time and filters event queries by tenant.

Set a strong stable `AURA_SECRET_KEY` in the server environment. If unset, the backend generates a process-local random key; tokens become invalid after restart and are unsuitable for multiple workers. The project remains a prototype: rate limiting, verified email, refresh tokens, MFA, invitation expiry, and production operations are not implemented. WebSocket authorization is checked on connect; reconnect after session changes. Keep it on a trusted network and avoid sensitive production data.
